Devkit: one source for Claude workflows and CI

One public repo holds one Claude plugin and four reusable CI workflows. Private repos use the latest version. Registry pins a tag because it has outside contributors.

Owner Jim Boone Date 2026-10-26 Status Draft Repo unibrain1/devkit (public)

Summary

Today, each project has its own copy of the milestone commands, review agents, and Claude CI workflows. The copies drifted apart. Registry and MyGunLog now make the same CI change by hand, one repo after the other.

This design moves the shared parts into one repo, unibrain1/devkit. It is sized for one developer. It solves the double work and adds as little new process as possible. Registry is the starting point because its workflow is the most mature.

Problems

  • Drift. start-issue, finish-milestone, and release-milestone exist in up to 5 repos, and each copy is different.
  • Three generations of Claude CI. The review workflow is 1,052 lines in Registry, 696 in MyGunLog, and 125 to 212 in the other repos.
  • Three secret scanners. MyGunLog uses gitleaks. BurgessGunWorks and TheSommelier use trufflehog. The other repos use none.
  • Commands depend on project scripts. Registry commands call about 20 scripts in scripts/, for example check-plan-state.sh and resolve-base-branch.sh.
  • Two copies of the agents. ~/.claude/agents holds older versions of five Registry agents.

The flow plugin

One plugin holds everything that is not specific to one tech stack:

  • The milestone and issue commands from Registry, and /flow:setup.
  • The method: a flow:workflow skill, and the hotfix skill.
  • The generic agents: code-reviewer, silent-failure-hunter, senior-architect, and the others. See "Generic agents" below.
  • The generic workflow scripts in bin/. Claude Code puts a plugin's bin/ on the command path, so commands call the scripts by name.
  • Optional vault steps in four commands. See section 13.

Commands read project facts from a reference file

Shared commands cannot name composer phpstan or npm test. Each project has .claude/project.md:

# Project facts for devkit commands

- test: `docker compose exec -u www-data app composer test:full`
- test_quick: `docker compose exec -u www-data app composer test:quick`
- lint: `composer phpstan`
- format: `composer cs:fix`
- verify: `scripts/run-verification-suite.sh`
- deploy: see `docs/development/DEPLOYMENT.md`
- standards: `docs/development/CODING_STANDARDS.md`
- plans: `docs/plans`
- release_notes: `docs/releases/RELEASE_NOTES_{version}.md`
- ledger: `docs/development/CLEANUP_LEDGER.md`
- private_paths: `docs/plans _noupload`

- issue_checks: `scripts/check-baseline-hygiene.sh`
- milestone_checks: `scripts/check-deploy-sheet-fresh.sh`
- release_checks: `scripts/check-deploy-sheet-fresh.sh`
- vault: `Projects/Elan Registry/Elan Registry.md`

Optional-key guard. If an optional key is missing, the shared command skips that step with no error. A shared command never runs a stack script by name. Stack scripts, for example Registry's deploy sheet, fix scripts, and phpstan baseline check, stay in the project, and a key points to them.

No silent skips. A typo in a key name, for example release_check, must not look like "this project has no such check". Two rules prevent this:

  • Unknown keys stop the command. In its first step, each shared command runs flow-project-check. The script compares each key in project.md with the known list. An unknown key stops the command, and the error names the nearest known key. A missing test or lint key also stops the command.
  • Each command reports its skips. At the end, each shared command prints a "Skipped steps" list with the reason for each step, for example release_checks: no key in .claude/project.md. This shows a key that a migration lost.

The vault key is optional. It gives the path of the project's hub note in the vault. A repo with no vault key gets no vault steps. In a public repo, the key shows only the note path, not the note.

  • No load in normal sessions. Claude Code loads CLAUDE.md in every session. It does not load this file. Each shared command reads the file in its first step. If the file is missing, the command stops and tells you to make it.
  • No @ import. An @.claude/project.md line in CLAUDE.md loads the file in every session, which is the bloat to avoid. If CLAUDE.md names the file, it uses a plain path.
  • Readable by scripts too. Each line has the form - key: `command`. The scripts in flow/bin/ get a value with one sed line, so no JSON file is needed.
  • One owner for each fact. If CLAUDE.md already lists the test command for normal work, keep it there. project.md holds only what the shared commands need. Do not copy text between the two files.

Commands get the repo visibility and name from gh repo view --json visibility,nameWithOwner. No script in flow/bin/ names a repo.

Generic agents

The Registry agents name PHP, UserSpice, and Registry files. The flow agents keep each role and review method, without stack rules:

  • Each agent reads CLAUDE.md, the files in the standards key, and the project's .claude/rules/ for the files it reviews.
  • Stack rules move to the project. For Registry, the PHP and UserSpice text from its agents moves to .claude/rules/ when Registry migrates.
  • The five global agents in ~/.claude/agents merge into this generic base.

Upstream plugins

A third-party skill that has its own plugin is not copied into devkit. The devkit marketplace lists it with its upstream repo as the source, pinned to a full commit SHA. In v0.1.0, this is asd-ste100 from danyuchn/asd-ste100-skill (MIT).

  • No copy. Nothing can drift, and the attribution and LICENSE stay with upstream. docs/sources.md records the pin.
  • Turn it on. A project turns on asd-ste100@devkit next to flow@devkit. The skill name is asd-ste100:asd-ste100.
  • Source type. The entry uses a url source with the HTTPS clone URL and the sha, not a github source. Claude Code clones a github plugin source over SSH only, so the install fails on a network that blocks SSH to github.com. upstream-sync.yml reads both source types.
  • Stay in sync. Each week, upstream-sync.yml compares upstream HEAD with the pin. If upstream moved, it opens a PR that changes the SHA and links the upstream diff. You read the diff and merge. A bad upstream change reaches no repo until you merge.

Milestone limit rule

/flow:start-milestone counts the milestones in progress. A milestone is in progress when its milestone/* branch exists on origin. The command stops if a private repo already has 1 such branch, or a public repo already has 2.

  • Count branches, not GitHub milestones. An open GitHub milestone is a plan. Registry has 13 open milestones (v2.31 to v2.43) and MyGunLog has 2, but neither repo has a milestone/* branch. A count of GitHub milestones would block both repos.
  • How to count. git ls-remote --heads origin 'milestone/*'. A script in flow/bin/ runs it, so all commands use the same count.
  • End of a milestone. /flow:release-milestone deletes the milestone/* branch after the merge. If the branch stays, the count stays too.

The method and setup

The Registry commands refer to Registry's ISSUE_WORKFLOW.md and to workflow sections in its CLAUDE.md. Other projects do not have these docs, and a plugin cannot ship a CLAUDE.md. So flow carries the method in three parts:

  • flow:workflow skill. The full method, from ISSUE_WORKFLOW.md, Registry's CLAUDE.md, and its rules planning-docs.md and ci-workflows.md. Examples: the four loops, the plan gate, the review rules, the cleanup ledger, backlog age-out, the gh gotchas, and the main-match rule. Commands refer to its sections by name. Claude loads it on demand, so it adds no context to a normal session.
  • hotfix skill. The hotfix procedure. Its deploy step reads the deploy key.
  • A marked block in CLAUDE.md. About 10 lines: the branch model, the command order, the hand-off rule, and a pointer to the skill. It loads in every session, so the order and the hand-off rule are always present. Each command also states the hand-off rule in its last step, so a session without the block behaves correctly.

/flow:setup. A plugin has no install step, so a command does the job. You run it one time in each repo, and again after a devkit release that changes the block:

  • It creates .claude/project.md from a template and asks for the test and lint commands.
  • It lists the labels that the method uses and that the repo does not have. It creates them only after you approve the list. It never changes a label that exists.
  • It shows the CLAUDE.md block as a diff and writes it only after you approve. The block is between <!-- flow:begin rev N --> and <!-- flow:end -->. N is the block revision in the flow template. It changes only when the block text changes, because the plugin has no version field to compare. On a later run, setup replaces only the text between the markers.

SessionStart check. A flow hook checks that project.md exists and that the block has the current revision. If one is wrong, it prints one line: "Run /flow:setup". If both are correct, it prints nothing.

Command names

Plugin commands have a prefix: /flow:start-issue, @agent-flow:code-reviewer. If a project has its own command with the same base name, /start-issue runs the project copy. Each migration must therefore delete the old project copies.

Public repos: repo settings, not workflow files

GitHub gives these free to public repos. You turn them on in each repo's settings, so they need no workflow file and no maintenance:

  • CodeQL default setup
  • Secret scanning and push protection
  • Dependabot alerts

Registry's own codeql-analysis.yml can stay or change to default setup. Release automation stays in the projects that have it (mock-brevo and Monitoring).

A caller

# .github/workflows/claude-code-review.yml
name: Claude Code Review
on:
  pull_request:
    types: [opened, synchronize, ready_for_review, labeled]
  issue_comment:
    types: [created]
  workflow_dispatch:
    inputs:
      pr_number: { type: number, required: false }
jobs:
  claude-review:
    permissions:
      contents: read
      pull-requests: write
      issues: read
      id-token: write
    uses: unibrain1/devkit/.github/workflows/claude-review.yml@main
    with:
      pr_number: ${{ inputs.pr_number }}
    secrets:
      CLAUDE_CODE_OAUTH_TOKEN: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
  • Each caller job grants the permissions that the shared jobs need. A new repo gives the workflow token read access only, and a called job cannot get more than its caller. Without the block, the run fails at startup. docs/ci-workflows.md lists the block for each workflow.
  • Callers pass each secret by name. secrets: inherit does not work across orgs, and the repos are in three orgs.
  • Devkit keeps Registry's rule to pin third-party actions to full SHAs. Dependabot in devkit bumps them one time for all repos.
  • The review workflow keeps Registry's fork-safety rules (#1688) and its Dependabot skip.
  • Each repo names its review caller .github/workflows/claude-code-review.yml, the same name as today. The flow scripts use this name. The reusable workflow gets the caller path from github.workflow_ref, so it names no file.
  • The review has three jobs: pr-to-milestone-review for issue PRs and ad hoc PRs, milestone-review for milestone/* to main or the deep-review label, and comment-deep-review for a "@claude deep-review" comment from OWNER or COLLABORATOR.
  • The CI workflows do not load flow. The prompts read CLAUDE.md, .claude/project.md, and .claude/rules/. Two optional inputs hold project additions, both empty by default: extra_allowed_tools in both Claude workflows, and extra_instructions in claude-review.yml only. In claude-code-action v1.0.261, tag mode takes no added text, so project text for @claude goes in CLAUDE.md or .claude/rules/.

Keep devkit main safe

  • Changes go to devkit through a PR. self-test.yml must pass before the merge. It lints the workflows and checks that the plugin loads.
  • Test a risky change in one private repo first. Point that repo at the PR branch, then set it back to main.
  • Each devkit release bumps version in plugin.json. If the version stays the same, Claude Code keeps the old cached copy. Or leave out version, and each new commit counts as a new version. This is simpler for main.

When a new version reaches your machine

With autoUpdate: true, Claude Code checks for updates after the first message of a session, after a random delay of up to 10 minutes. The running session keeps the old version until /reload-plugins or the next launch. To get the new version at once, run claude plugin marketplace update devkit.

One machine, two refs

Claude Code keeps one devkit entry for each machine, under the name in marketplace.json. When a session starts, it points that entry at the project's ref and loads that version. A session open in another project then shows "plugins changed, run /reload-plugins". With two projects open, run /reload-plugins only in the project that you opened last. A second name such as devkit-stable does not work: Claude Code ignores a settings key that is not the same as the name in marketplace.json, and gives no error.

The main-match rule

In every repo, a Claude workflow on a branch must match the copy on main, or it does not run. This is not a Registry rule. It comes from GitHub and from claude-code-action:

  1. GitHub. For comment, issue, schedule, and pull_request_target events, GitHub runs only the workflow file on the default branch. A branch copy never runs. @claude in claude.yml is this case. A workflow_dispatch workflow must exist on the default branch.
  2. claude-code-action. For a pull_request event, the action compares the workflow file on the PR head with the copy on the default branch. If the two are different, the action skips the review. A PR that edits a Claude workflow is never reviewed by Claude (Registry #1919).

Registry writes this down in .claude/rules/ci-workflows.md. Its review gate reports the skip as a warning, not a failure. The other repos have the same limit, but have no rule or gate for it.

The devkit review gate gives a warning only when the branch or its base branch changed the file. If only main changed it, the branch has an old copy, for example a branch cut from a tag. Then the gate fails. It tells you to copy the file from main onto the base branch if that branch is also old, and then to update the PR branch from its base branch (devkit #32).

Rules that follow

  • Edit a caller file only at a milestone boundary, in every repo. That is after /release-milestone and before /start-milestone, when no milestone or issue branch is open. This covers the migration PR, a new input, and Registry's pin bump. If you edit a caller in the middle of a milestone, each open branch has the old file, and the review skips its PRs.
  • In a repo with no milestone branches, edit a caller when no other PR is open, or update the open branches from main after the merge.
  • Dependabot ignores unibrain1/devkit in Registry. Its bump PR targets main at a random time, which breaks the rule above.
  • Hotfix PRs are safe. A hotfix branch starts from main, so its pins match main.
  • Keep the caller interface stable. Give each new input a default value, so callers do not need an edit. A caller edit costs one skipped review in each repo.
  • Keep job names stable. A reusable job shows as <caller job> / <reusable job>. Branch protection and Registry commands use these names, for example pr-to-milestone-review. A rename in devkit breaks required checks in all repos at once.
  • Test CI changes in a sandbox repo. A consumer PR that points its caller at a devkit branch has a caller that is different from main, so the review skips it. Use a small private repo, unibrain1/devkit-sandbox. You can change its main at any time, so its caller on main can point at a devkit branch.

A day with devkit

Morning: normal work in a private repo

  1. You open Claude Code in TeamCroc. Within 10 minutes after your first message, Claude Code gets the newest flow from devkit main.
  2. You run /flow:start-issue 42. The command reads the test and lint commands from TeamCroc's .claude/project.md.
  3. The same file has a vault key, so /flow:start-issue searches the vault for decisions and notes about the issue. It shows you the matches in the plan.

Second brain (v1.1)

This part ships in v1.1, after the pilot (rollout phase 4). The Baalda vault UniBrain is the second brain. It holds what a repo does not: why you made a choice, ideas you parked, open questions, and status across milestones. Claude Code reaches it through the Baalda MCP server, which is in the user settings, so every session on your machine has the tools.

The vault uses PARA folders (Projects/, Areas/, Resources/, Archive/), plus Inbox/, Daily/, People/, and Reviews/. Each project has a hub note with the same name as its folder, for example Projects/The Sommelier/The Sommelier.md. The Sommelier is the trial project, imported on 2026-10-26.

  • The repo wins for code facts. A hub links to the repo and does not copy its README. Doc snapshots in a project's Docs/ folder name their source commit.
  • The vault is personal. Contributors and CI have no access to it.

Each vault step is optional

Registry is public and has outside contributors. A contributor's session has no Baalda access. Each vault step starts with this guard:

If .claude/project.md has no vault key, or the Baalda tools are not available,
skip this step. Do not stop the command.

A vault step never blocks a command. If a vault write fails, the command reports it and continues.

Sensitive notes

Health, legal and biography notes stay in UniBrain, in Areas/Health/ and Areas/Personal/. A second vault costs money, so it waits until there is a need.

  • No technical limit. Baalda sets access for each person, not for each Claude session. Every session connects as you, so every session can read these notes. A hook cannot split one vault, because search_notes searches the whole vault.
  • Written rule. The ~/.claude/CLAUDE.md text below tells sessions not to open these folders unless you ask. The AGENTS.md files in the two folders say the same.
  • Claude apps. If you connect Baalda to the Claude desktop or mobile app, that app can read these notes too.

Upgrade path. If you pay for a second vault later, move these notes to a Private vault. Then a PreToolUse hook on mcp__baalda__.* can block calls with the Private vault ID, except in sessions in the folders you allow. The brain plugin can ship that hook.

Token cost

  • Commands read the vault on demand. No hook loads a hub note at session start.
  • Keep each hub note to about one screen. Put long material in linked notes.
