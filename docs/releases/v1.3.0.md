# devkit v1.3.0: Review trusts only what it should

Date: 2026-10-31

## Summary

A maintainer can trust a green review Gate. Only real human rebuttals and
real review runs count, and no caller, fork, or bot comment can turn the
Gate green.

## Upgrade

- `flow-release-milestone` waits for the required checks of `main` on the
  PR head before it merges (#78). The default limit is 30 minutes.
  `--checks-timeout <minutes>` changes it. `/flow:release-milestone` runs
  the script in the background.
- A required check that fails stops the run with exit 2. A required check
  that does not pass in the time limit also stops it with exit 2. Nothing
  merges. A PR head that the script did not push also stops the wait at
  once with exit 2. The name of each required check must equal its name in
  `gh pr checks`. A name that does not match counts as pending.
- In a `claude --plugin-dir plugins/flow` session, `flow-release-milestone`
  runs a copy of its `bin` folder from the `--reviewed-sha` commit (#77).
  A run from the work tree with no `--reviewed-sha` stops with exit 1.
  Until `main` has the v1.3.0 merge commit, `main` has the v1.2.0 script,
  which has no copy step. Run the v1.3.0 release session, and each rerun
  or resume of it, from the milestone branch.
- `/flow:review-milestone` now runs `flow-review-workflow-files` in Step 4.
  It finds each review workflow file that the PR changes, not only
  `claude-code-review.yml` (#76). A project must name its caller file
  `.github/workflows/claude-code-review.yml`.
- `flow-verify-ci-review` compares each review workflow file at the PR head
  with `main`, as the CI step does. So `/flow:finish-issue` also offers to
  go on without the CI review after an earlier PR changed the file.
- `/flow:review-pr`, `/flow:address-pr-comments`, `/flow:execute-plan`, and
  `/flow:finish-milestone` now ask all decisions in one round (#63). One
  `AskUserQuestion` call has at most 4 questions. A round with more than 4
  decisions uses more calls, one after the other.
- Each review job in `claude-review.yml` now stops and fails on a fork PR
  (#42). A person reviews a fork PR. Before, `milestone-review` could pass
  the Gate on a fork PR that edited the caller file.
- The review keeps a `github-actions` comment only when it ends with a
  verdict line. It reads it as an earlier review, never as a rebuttal
  (#39, #44).
- The review jobs fail when `extra_allowed_tools` has a `gh`, git,
  `WebFetch`, or GitHub MCP rule, a `Bash` rule that allows each command,
  a `Bash` rule with shell syntax in its first word, or a bare `Read`,
  `Grep`, or `Glob` (#40). Put a comma, not a space, between rules.

## Verification

- Check out the `v1.3.0` tag. Run `bash tests/run.sh`. All tests must pass.
- Run the lint set: markdownlint, yamllint, actionlint, and shellcheck. CI
  runs the tests and the lint on `ubuntu-24.04` and `macos-15`.
- In devkit, run `flow-review-workflow-files`. It prints
  `.github/workflows/claude-code-review.yml` and
  `.github/workflows/claude-review.yml` (#76).
- Run `bash tests/bin/test-flow-release-milestone.sh`. Cases W1 to W13
  cover the wait for required checks (#78). Cases T1 to T9 cover a script
  in the work tree (#77).
- Run `bash tests/commands/test-decision-rounds.sh`. It checks that
  `/flow:review-pr`, `/flow:address-pr-comments`, `/flow:execute-plan` and
  `/flow:finish-milestone` ask all decisions in one round (#63).
- Run `bash tests/workflows/test-review-fork-stop.sh`. It checks that each
  of the three review jobs stops a fork PR, and that the
  `milestone-review` stop fails the job (#42).
- Run `bash tests/workflows/test-review-comment-trust.sh`. It checks the
  `person` and `earlier-review` roles, and that the verdict rule matches
  the flow scripts (#39, #44). It also checks that the `PR_NUM` line of
  each fetch step equals the `PR_NUM` line of Post review (#49).
- Run `bash tests/workflows/test-review-extra-tools.sh`. It runs the
  `extra_allowed_tools` check on each rejected form (#40).
