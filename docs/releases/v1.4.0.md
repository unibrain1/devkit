# v1.4.0 — Repo families

Date: 2026-11-24

## Summary

A maintainer can start a new repo from a family template, or move an existing repo to its template. Repos in one family then differ only in content and deploy target.

## Issues Resolved

- [#113](https://github.com/unibrain1/devkit/issues/113) — `/flow:setup` adds the missing baseline files: pre-commit hooks, Claude and secrets-scan callers, and Dependabot.
- [#118](https://github.com/unibrain1/devkit/issues/118) — Family A templates cover static sites, and `node-site.yml` gets an optional `lint_script` input for the host CSS and PHP lint.
- [#115](https://github.com/unibrain1/devkit/issues/115) — A stack-neutral Family W template for web apps has command placeholders, two host texts, and an `.env` block hook.
- [#114](https://github.com/unibrain1/devkit/issues/114) — A Family B template and a reusable container-image workflow. A hotfix now gets a patch tag, so `latest` moves.
- [#116](https://github.com/unibrain1/devkit/issues/116) — The Family I template for iOS apps runs SwiftLint at commit and `xcodebuild test` at push, with no macOS CI.
- [#117](https://github.com/unibrain1/devkit/issues/117) — `/flow:new-project` asks the setup questions, recommends a family, and fills the template with `flow-template` to create a repo.
- [#92](https://github.com/unibrain1/devkit/issues/92) — `/flow:setup` installs or checks the enabled plugins, and the session start reports a missing or old plugin.

## Deployment instructions

- #113: in each repo, run `/flow:setup`. Then do all the manual steps in [docs/baseline.md](../baseline.md).
- #113, #92: a repo that has its own copy of `.claude/settings.json` does not get the new allow rules. Add `Bash(flow-baseline --status:*)` and `Bash(flow-plugins:*)` to `permissions.allow`, or `/flow:setup` asks for approval each time.
- #118: no step for an existing repo. The templates are for `/flow:new-project` (#117). A static site moves to its template in phase 3.
- #115: no step for an existing repo. MyGunLog moves to the template in phase 3. Registry moves at a Registry milestone boundary.
- #114: before a container repo moves to `container-image.yml`, change its host pull tag to `latest` or a version (Monitoring: `:main` to `:latest`). See [ci-workflows.md](../ci-workflows.md#host-pull-tag).
- #114: `flow:hotfix` now runs `flow-release-hotfix`, which makes the hotfix tag `vX.Y.(Z+1)`. A repo that uses devkit `main` gets this rule after the release, when its plugin is updated (see the #92 step). Registry and Registry2 get it at the next pin bump, and then remove the four-part tag step from `docs/development/DEPLOYMENT.md`.
- #114: if an open milestone has the next patch version, `flow-release-hotfix` stops at the tag step, after the hotfix PR is on `main`. MyGunLog has tag `v2.7.4` and the open milestone `v2.7.5`. Before a hotfix there, change the version of that milestone: the GitHub milestone title and the `milestone/v2.7.5` branch. See #139.
- #116: no step for an existing repo. DryFireTimer moves to the `ios-app` template in phase 3.
- #92: in each repo, run `/flow:setup --check`. If it reports a missing or old plugin, run `/flow:setup` to install or update it. Then run `/reload-plugins`. In a repo that uses devkit `main`, the session start reports an old plugin again after each later devkit change. Run `/flow:setup` again then.
- #117: no step for an existing repo. Start each new repo with `/flow:new-project` in an empty folder.
- #116, #117: the `ios-app` allow rule is now the exact test command, not `Bash(xcodebuild test:*)`.
